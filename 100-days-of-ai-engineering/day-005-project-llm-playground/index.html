The “why?” ladder

Why estimate tokens before calling a model?
So you can predict cost and check the prompt fits the window (Day 2), instead of finding out from a bill or an error.
Why keep prices in a JSON file?
Prices change often. Data in a file can be updated without touching code, and tests can use fixed prices.
Why write tests for a tiny calculator?
Money maths hides silent bugs (rounding, units). Tests keep it correct when you change something later.
Why does the README matter so much?
Most reviewers decide in 30 seconds. A clear what, demo and how-to-run shows you can communicate and finish things.
Pitfalls: hard-coding prices in code · skipping the README until “later” · committing an API key (this project doesn’t need one, so don’t add any).

Coding question: the cost calculator

Easy–medium · 15–20 min · this is the heart of your project. Attempt it first, then the hint, then the solution.

Task. Write estimate_cost(text, expected_output_tokens, in_price_per_m, out_price_per_m). Estimate input tokens as ceil(len(text) / 4). Prices are per million tokens. Return a dict with tokens_in, cost_in, cost_out and total, each cost rounded to 6 decimals. Raise ValueError if any number is negative.
estimate_cost("a" * 400, 500, 2, 8)
# {"tokens_in": 100, "cost_in": 0.0002, "cost_out": 0.004, "total": 0.0042}

estimate_cost("abc", 10, 2, 8)["tokens_in"]   # 1  (3 chars rounds up)
estimate_cost("", 0, 2, 8)["total"]           # 0.0
estimate_cost("hi", -1, 2, 8)                 # ValueError
💡 Hint (open only after trying)Use math.ceil(len(text) / 4) for tokens. Cost per side is tokens * price / 1_000_000. Check min(...) < 0 first and raise before doing any maths.
✅ Solution + explanation (open after your attempt) 
import math

def estimate_cost(text, expected_output_tokens, in_price_per_m, out_price_per_m):
    if min(expected_output_tokens, in_price_per_m, out_price_per_m) < 0:
        raise ValueError("values must be non-negative")
    tokens_in = math.ceil(len(text) / 4)
    cost_in = tokens_in * in_price_per_m / 1_000_000
    cost_out = expected_output_tokens * out_price_per_m / 1_000_000
    return {
        "tokens_in": tokens_in,
        "cost_in": round(cost_in, 6),
        "cost_out": round(cost_out, 6),
        "total": round(cost_in + cost_out, 6),
    }
How it works
  1. Validate first so bad input fails loudly instead of producing a negative bill.
  2. ceil because a partial token still costs a whole token; 3 characters can’t be 0.75 of a token.
  3. Divide by 1,000,000 because prices are quoted per million tokens. Input and output are priced separately (Day 2).
  4. round(…, 6) hides tiny floating-point noise like 0.0042000000000000006.
  5. Next: swap the chars ÷ 4 line for a real tokenizer behind a flag, and read prices from prices.json.
