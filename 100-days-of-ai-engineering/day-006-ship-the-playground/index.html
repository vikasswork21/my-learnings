The API in 20 lines

# app.py
import json
from fastapi import FastAPI, HTTPException
from pydantic import BaseModel, Field
from playground_core import estimate_cost

app = FastAPI(title="LLM Playground")
PRICES = json.load(open("prices.json"))

class EstimateIn(BaseModel):
    text: str
    model: str
    expected_output_tokens: int = Field(500, ge=0)

@app.post("/estimate")
def estimate(body: EstimateIn):
    p = PRICES.get(body.model)
    if p is None:
        raise HTTPException(404, f"Unknown model: {body.model}")
    return estimate_cost(body.text, body.expected_output_tokens, p["in"], p["out"])

@app.get("/models")
def models():
    return list(PRICES)

5 · Definitions

Endpoint
A URL plus method (like POST /estimate) that does one job.
Schema (Pydantic)
A class describing the shape and rules of the data. Bad input is rejected automatically.
OpenAPI /docs
The interactive page FastAPI builds for you so you can try the API in a browser.
Pinning a repo
Showing up to 6 repos at the top of your GitHub profile.

6 · The “why?” ladder

Why share one core between the CLI and the API?
One place to fix bugs and change prices. Both doors stay consistent, and you test the logic once.
Why validate input with Pydantic?
Bad data is stopped at the edge with a clear error, so your core never has to guess what it received.
Why add a demo screenshot to the README?
People decide in seconds. A picture proves it works before they read any text or run any code.
Why pin the repo?
Recruiters look at your profile top first. Pinned repos are the ones you want them to see.
Pitfalls: API logic copied from the CLI instead of shared · no error for an unknown model · pushing without a README · leaving secrets (none needed here) in the repo.

9 · Coding question: pick the cheapest models

Easy–medium · 15–20 min · skills: dicts, sorting, reusing a function. Attempt it first, then the hint, then the solution.

Task. estimate_cost is already written for you (it is yesterday’s function). Write cheapest_models(text, expected_output_tokens, prices, top_n=2). prices maps a model name to {"in": ..., "out": ...} (per million tokens). Return the top_n cheapest models as a list of (name, total_cost) tuples, cheapest first. If two models cost the same, order them by name.
prices = {
  "small":  {"in": 0.5, "out": 1.5},
  "medium": {"in": 2,   "out": 8},
  "large":  {"in": 10,  "out": 30},
}
cheapest_models("a" * 400, 500, prices)
# [("small", 0.0008), ("medium", 0.0042)]

cheapest_models("a" * 400, 500, prices, top_n=1)   # [("small", 0.0008)]
💡 Hint (open only after trying)Loop over prices.items(), call estimate_cost(...)["total"] for each, collect (name, total) tuples, then sort with key=lambda x: (x[1], x[0]) and slice [:top_n].
✅ Solution + explanation (open after your attempt) 
def cheapest_models(text, expected_output_tokens, prices, top_n=2):
    results = []
    for name, p in prices.items():
        total = estimate_cost(text, expected_output_tokens, p["in"], p["out"])["total"]
        results.append((name, total))
    results.sort(key=lambda x: (x[1], x[0]))
    return results[:top_n]
How it works
  1. Reuse, don’t rewrite. The cost maths lives in one place, so a fix there fixes every caller (the one-core idea).
  2. Sort by a tuple (cost, name): Python compares the cost first and the name only on a tie, so results are deterministic.
  3. Slice last with [:top_n]; asking for more than exist just returns them all, with no error.
  4. Cost: m models means m calls plus an O(m log m) sort.
  5. Real-world catch: cheapest is not best. Later you will also weigh quality and speed when choosing a model.
