1 · The gist

Everything an LLM does is measured in tokens. Tokens decide what fits (context window), what you pay (cost) and how long you wait (latency).

3 · Analogies

Context window = whiteboard. The model can only work with what’s on the board. When it’s full, the oldest notes get wiped. Nothing off the board exists for it.
Cost = auto-rickshaw meter. You pay per token, for reading (input) and writing (output), and writing costs more per unit.
Latency = Hyderabad traffic. First a wait before the vehicle moves (time to first token), then a steady speed (tokens per second).

4 · Definitions

Token
A reusable chunk from a fixed vocabulary. Common words are 1 token; rare words split into pieces.
Context window
The maximum tokens (input + output) the model handles in one call, e.g. 128k.
Input / output tokens
Input = everything you send. Output = what the model writes back. Billed separately.
TTFT
Time to first token: the wait before the answer starts appearing.
Tokens per second
How fast the answer streams out once it starts.
max_tokens
A cap you set on the answer length. Too low = the answer is cut off mid-sentence.

6 · The “why?” ladder

Why tokens and not words or letters?
A fixed vocabulary of reusable chunks handles any word, typo or new name, while keeping sequences much shorter than letters would.
Why do Hindi or Telugu text cost more than English?
Tokenizers are trained mostly on English text, so other scripts are split into more, smaller pieces. Same meaning, more tokens, more cost, less room.
Why is output pricier than input?
Input tokens are processed together in parallel. Output tokens come one at a time: each needs a full pass through the model (Day 1’s loop).
Why do long chats get slower and costlier?
The model has no memory between calls. The app resends the whole history every turn, so input tokens grow every turn.
Why not stuff everything into the window?
It costs more, starts later, and facts buried in the middle of a huge input are used less reliably. Picking only the relevant pieces is the idea behind RAG (Phase 2).
Pitfalls: assuming characters ≈ tokens · forgetting the answer shares the window · setting max_tokens so low that answers get cut off.

10 · Coding question: trim chat history to fit the window

Easy–medium · 15–20 min · skills: lists, loops, reverse traversal. Attempt it first, then the hint, then the solution.

Task. messages is a list of dicts with role and tokens. messages[0] is the system message and must always stay. Write trim_history(messages, limit, reserve_output) that keeps the system message plus the most recent messages that fit in limit - reserve_output tokens, returned in original order. Stop at the first message that doesn’t fit (no gaps). If the system message alone is too big, raise ValueError.
messages = [
  {"role": "system",    "tokens": 50},
  {"role": "user",      "tokens": 200},
  {"role": "assistant", "tokens": 300},
  {"role": "user",      "tokens": 100},
  {"role": "assistant", "tokens": 250},
  {"role": "user",      "tokens": 80},
]
# budget = 800 - 200 = 600
trim_history(messages, 800, 200)
# keeps system(50) + user(100) + assistant(250) + user(80) = 480 tokens
# the assistant(300) message would not fit, so it and everything older is dropped

trim_history(messages, 100, 60)   # budget 40 < system 50 -> ValueError
💡 Hint (open only after trying)Subtract the system message from the budget first. Then walk the remaining messages from newest to oldest, keeping a running “tokens left”. When one doesn’t fit, break. Reverse the kept list at the end.
✅ Solution + explanation (open after your attempt) 
def trim_history(messages, limit, reserve_output):
    budget = limit - reserve_output
    system = messages[0]
    if system["tokens"] > budget:
        raise ValueError("system prompt too large")
    remaining = budget - system["tokens"]
    kept = []
    for msg in reversed(messages[1:]):
        if msg["tokens"] > remaining:
            break
        kept.append(msg)
        remaining -= msg["tokens"]
    return [system] + kept[::-1]
How it works
  1. Budget first. The answer shares the window, so we reserve room for it before counting input.
  2. Newest first. Recent turns matter most to the next answer, so we fill the budget from the end backwards.
  3. Why break and not continue? Skipping a big message and keeping an older small one would leave gaps: an answer without its question. Contiguous recent history stays coherent.
  4. Reverse at the end because we collected newest-first and the model needs chronological order.
  5. Cost: O(n) time, one pass. The running “remaining” is the same idea as a prefix sum (today’s DSA topic).
What would a real app do differently? Count tokens with the model’s tokenizer instead of trusting stored numbers, and summarise the dropped part instead of deleting it, so key facts survive.
